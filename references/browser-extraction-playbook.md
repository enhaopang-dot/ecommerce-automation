# 网页取数 SOP（开放平台 API 走不通时的替代路线）

> 适用：抖店类目未批、电商罗盘无 API、各平台后台导出
> 性质：**临时通道**。平台一改版就断，API 通了就退役。
> 最后核实：2026-10-27（事实来源为某女装客户项目实战脚本与迭代记录）

## 通用原则

1. **复用一个持久化浏览器 profile**，保住登录态，别每次重新扫码
   - 现成 profile：`（本地浏览器配置目录）`
   - 单实例锁：脚本异常退出后要清 Edge 残留进程，否则下次起不来
2. **优先「后台导出」而不是「翻页抓接口」**。列表接口普遍带签名（如 a_bogus），改页码直调会报错；导出是官方给的合法通道，字段还更全。
3. **只读**：不改单、不发货、不动库存、不改价。
4. **能拿子账号就拿子账号**，主账号只用于一次性授权。
5. **短信验证要人配合**，脚本里留 flag 文件 + 等码机制，不要死等。

## 1. 抖店商家后台（fxg.jinritemai.com）

| 结论 | 全自动不稳，**批量历史数据建议让商家自己导**，日常增量再用脚本 |

## 4. RPA（影刀 / 来也）

本质与 Playwright 同一套：模拟点击 + 导出。差别在维护责任和成本：

| 维度 | Playwright 自写 | RPA 工具 |
| --- | --- | --- |
| 成本 | 无许可证费，自己维护 | 许可证 + 学习成本，组件别人维护 |
| 稳定性 | 平台改版要自己改脚本 | 同样会断，改起来未必更快 |
| 适合 | 一次性批量、与已有 Python 链路打通 | 业务同事自己跑、跨系统串联 |

结论：**能自写就自写**，RPA 只在需要业务人员脱离技术也能操作时才值得上。

## 5. 风险与退役条件

- 风控：高频刷新、异常翻页会触发验证码甚至限流，操作间隔 ≥3 秒
- 封号成本：客户店铺账号异常会波及客户生意，**绝不拿主账号做高频操作**

### 退役判定：API 通了不等于全退役

判据是「**这个数据源的字段能否被 API 全覆盖**」，不是「API 通没通」。下表是 **2026-10-27 口径**，按 `SKILL.md` 的时效纪律每季度复核，平台发版/发公告时立即复核。

| 数据源 | 2026-10-27 口径 | 备注 |
| --- | --- | --- |
| 抖店后台订单导出 | 类目批下后可退役 | 订单/商品/物流/售后都在开放范围内 |
| 电商罗盘经营分析 | 暂不能退役 | 官方 FAQ 2026-08-06 称接口未开放；若未来开放可改走 API |
| 创作者中心 → 内容管理导出 | 可部分退役，保留定期补字段 | 完播率、5s 完播率、封面点击率、2s 跳出率、平均播放时长、主页访问量、粉丝增量，当日文档未见对应能力 |
| 创作者中心 → 投稿分析导出 | 同上 | 该入口约 90 天窗口 |

执行规则：某个平台 API 打通后，先列字段对照表，确认无缺口再停浏览器链路；有缺口就保留低频导出，并在台账注明「补哪几个字段」。缺口本身也要标核实日期——官方随时可能补齐。
